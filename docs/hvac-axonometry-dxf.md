# Аксонометрическая схема ОВ в DXF

Модуль `hvac.design_dxf` формирует предварительную однолинейную
аксонометрическую схему каждой системы из связанной тройки артефактов:
`hvac-terminal-layout-request`, `hvac-terminal-layout-response` и
`hvac-route-network-response`. Экспорт не выполняет расчёты и не изменяет
исходные JSON или модель Revit.

## Запуск

```powershell
python -m hvac.design_dxf `
  --request request.json `
  --terminal terminal-response.json `
  --route route-response.json `
  --out output-directory `
  --axon
```

Без `--axon` сохраняется прежний режим и создаётся только `plan.dxf`. С
`--axon` в новом каталоге `--out` создаются:

- `plan.dxf` — план из ТЗ-23;
- `axon-<systemId>.dxf` — отдельная аксонометрическая схема для каждой
  системы, присутствующей в route-response.

Входы обязаны иметь согласованные `requestId`, `sourceEvidence` и хеши, а
оба response-файла — статус `PRELIMINARY`. Каталог назначения имеет
write-once-семантику: существующий каталог не перезаписывается.

## Проекция

Применяется косоугольная фронтальная проекция типа cabinet. Оси `X` и `Z`
образуют фронтальную плоскость и сохраняются в истинном масштабе. Уходящая
в глубину ось `Y` проводится под углом 45° с половинным масштабом:

```text
X' = x + y * cos(45°) * 0.5
Y' = z + y * sin(45°) * 0.5
```

В реализации угол и коэффициент глубины заданы именованными константами
`AXON_RECEDING_AXIS_ANGLE_DEGREES = 45.0` и
`AXON_DEPTH_SCALE = 0.5`; готовые множители координаты `y` —
`AXON_COS_45_HALF` и `AXON_SIN_45_HALF`. Так геометрический смысл не
скрывается в числовых литералах. Значение `0.5` уменьшает визуальное
удлинение уходящих участков, а угол `45°` одинаково распределяет их вклад
по осям листа. Поэтому фронтальный контур `X-Z` остаётся в масштабе 1:1, а
направление `Y` читается как глубина без доминирования над схемой.

Проекция из трёх координат в две математически не обратима: разные точки
`(x, y, z)` могут дать одинаковые `(X', Y')`. Исходную пространственную
точку можно восстановить только при дополнительно сохранённом значении
`y` (тогда `x` и `z` находятся прямой подстановкой). DXF не следует
использовать как замену исходному route-response.

## Единицы и ноль этажа

Все координаты `positionMm` и размеры входных объектов трактуются как
миллиметры в системе координат проекта Revit
(`coordinateReference: revit-project-millimeters`). Результат DXF также
имеет единицы millimeters (`$INSUNITS = 4`); коэффициент проекции
безразмерный. В формулу проекции подставляется проектная координата `z` в
миллиметрах без изменения геометрического масштаба.

Ноль этажа определяется по исходному terminal-layout request. Экспортёр
берёт минимальное конечное значение `geometry.zFloorMm`; совместимый вход
может передать вместо него `geometry.floorElevationMm`. Если ни одного
конечного значения нет, datum принимается равным `0 мм`. Этот datum
используется только для высотных отметок у вертикальных участков. Текст
отметки показывает знаковую разность `(z - floorDatumMm) / 1000` в метрах,
например `+2.600 м` или `±0.000 м`. Ноль этажа не меняет абсолютные
проектные координаты геометрии в DXF.

## Сущности и слои

Слои определяются только через `hvac/dwg-layer-map.json`:

| Роль | Слой | ACI | Назначение |
| --- | --- | ---: | --- |
| `axonDucts` | `CRD_ОВ_АКСО` | 4 | Обычные участки аксонометрии |
| `axonCriticalDucts` | `CRD_ОВ_АКСО_ДИКТ` | 1 | Участки диктующей ветви |

Каждый участок системы создаётся одной незамкнутой полилинией. Слой
диктующей ветви исключительный: участок из `criticalPathSegmentIds`
помещается только на `CRD_ОВ_АКСО_ДИКТ` и не дублируется на
`CRD_ОВ_АКСО`. Поэтому сумма полилиний на двух аксонометрических слоях
равна числу участков системы.

Терминалы представлены блоками-значками с маркой модели, узлы врезки —
точками. Подпись участка содержит сечение (для круглого воздуховода —
`Ø...`) и расход в `м³/ч`. У вертикальных участков дополнительно выводится
высотная отметка относительно нуля этажа.

## Детерминированная раскладка подписей

Базовая позиция подписи задаётся параметром вдоль её участка. Если рамка
текста пересекает уже размещённую рамку, алгоритм проверяет фиксированную
последовательность следующих позиций вдоль того же сегмента. Порядок
участков, список смещений и проверка рамок не зависят от случайных чисел,
времени или порядка обхода DXF-сущностей. Один и тот же набор входных JSON
поэтому даёт одинаковую раскладку; в контрольной схеме текстовые рамки не
перекрываются.

## Границы версии

Экспорт имеет статус `PRELIMINARY` и предназначен для проверки связности и
читаемости схемы. В текущую версию входят однолинейные воздуховоды,
терминалы, точки врезок, подписи сечения/расхода, отметки стояков и
выделение диктующей ветви. Двухлинейная геометрия, фасонные части, рамка и
основная надпись листа не формируются.

После построения каждый документ проходит `ezdxf.audit`, затем повторное
чтение и аудит сохранённого файла. Для приёмки число полилиний должно быть
равно числу сегментов системы, а число терминальных значков — числу её
терминалов.
